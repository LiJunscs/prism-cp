# Hybrid Static Heterogeneous Parallelism — Research Roadmap

> **2026-09-16 近期执行方向更新：** 先执行 [SFT 二维 Dynamic CP 最小计划](SFT_2D_DYNAMIC_CP_MINIMAL_PLAN_20260916.md)：复用原生 sequence-wise DCP，验证同一 packed microbatch 内的 layer-group CP 与联合 packing；不增加 temporal cohort。先过机会、显存和正确性门禁，再决定生产 runtime。下文保留为静态异构路线的历史完整设计。

**Date:** 2026-09-11  
**Target stack:** latest Megatron-LM / Megatron-Core on NVIDIA H100; PyTorch DTensor allowed for fast mechanism prototypes  
**Primary workloads:** Qwen-like `GDN...GDN-GQA`; secondary workload: DeepSeek-like `CSA-HCA`  
**MoE/EP:** explicitly out of scope for this phase; expert mesh remains independent  
**Runtime philosophy:** **offline planning / predeclared plan, runtime fully static**  
**Main baseline:** best measured, correctness-matched uniform Megatron configuration — not Megatron default

---

## 0. Executive decision

The project is no longer centered on “heterogeneous CP + TMF” and is not trying to build another general-purpose Alpa/Hetu-style auto-parallel compiler.

The new target is:

> **Make static heterogeneous parallel execution a first-class capability for hybrid sequence models, while retaining Megatron’s production execution model.**

A training job is described by a **predeclared static heterogeneous execution plan**. The plan may be written manually or generated by an optional offline explorer. All process groups, mesh views, layouts, transition buffers, parameter/state ownership, and collective order are fixed before training begins.

The paper should first prove an **opportunity**:

1. different sequence mixers have meaningfully different optimal execution layouts on the same H100 topology;
2. a static heterogeneous layer-group plan beats the best uniform Megatron plan using the same kernels and training semantics;
3. the gain survives transition cost, backward, memory, optimizer, and checkpoint semantics.

Only after the manual oracle proves this opportunity should a general runtime or planner be built.

## 1. Research thesis

### 1.1 Core thesis

Modern hybrid sequence models contain a small number of mixer families with different computation–communication regimes:

- GQA: token-KV global attention;
- GDN/GDP: recurrent/prefix-state communication;
- HCA: highly compressed dense context;
- CSA: compressed context plus selection/index metadata.

A globally uniform Megatron parallel layout can therefore become a compromise.

The proposed system exposes:

\[
E_g = (A_g, P_g, S_g, T_{g\rightarrow g+1})
\]

for every **layer group** \(g\):

- \(A_g\): Activation Plane;
- \(P_g\): Parameter Plane;
- \(S_g\): Training-State Plane;
- \(T\): optional activation-layout transition.

The runtime executes the entire plan statically.

### 1.2 What is new vs. generic automatic parallelism

The claim is **not** that Alpa/FlexFlow/Hetu cannot express heterogeneous layouts.

The claim is:

1. the production runtime supports semantically explicit, predeclared, heterogeneous layer-group execution;
2. only correctness-certified execution templates enter the search space;
3. hybrid-mixer communication structure is used to generate a small useful candidate set;
4. the offline explorer is optional; the execution mechanism is independent of the policy that generated the plan.

### 1.3 Key design principle

> **Heterogeneous does not mean dynamic.**

All meshes/views/process groups are created before the measured training phase. There is no per-step process-group creation, online repartition search, or runtime graph rewriting.

## 2. Two training substrates

PP and FSDP are treated as **two separate primary substrates** in the first paper. They are not jointly optimized.

### 2.1 Substrate P: `PP × DP × TP × CP`

All four dimensions are compute-bearing dimensions.

Recommended first invariant:

\[
PP = \text{fixed},\qquad DP = \text{fixed}
\]

and within one PP stage / one DP replica:

\[
TP_g \times CP_g = M_{\text{intra}}
\]

where \(M_{\text{intra}}\) is usually the H100 NVSwitch island size (e.g. 8).

Example:

- GQA: `(TP=1, CP=8)`
- 3-layer GDN group: `(TP=4, CP=2)`

No extra independent samples are required, so MBS=1 remains legal.

**Primary paper performance path:** this substrate.

### 2.2 Substrate F: `FSDP/HSDP overlay + DP × TP × CP`

The true compute plane is:

\[
DP \times TP \times CP
\]

FSDP/HSDP is a parameter/training-state ownership overlay, not an additional useful-compute dimension.

Therefore:

\[
CP8,F1 \rightarrow CP2,F4
\]

is **not** a valid substitute for:

\[
CP8,TP1 \rightarrow CP2,TP4
\]

because standard FSDP materializes complete parameters before replicated compute.

The useful heterogeneity in this substrate is instead:

- same Activation Plane, different per-layer-group FSDP/HSDP parameter sharding degree;
- potentially different gradient/optimizer-state domains.

Example:

- Activation Plane stays CP8;
- GQA parameter group uses FSDP8;
- GDN parameter group uses FSDP4 + state replica factor 2.

This is a later gate, not the first opportunity test.

## 3. Three ownership planes

Do **not** call this a Cartesian “3D DeviceMesh”. Use **three ownership planes**.

### 3.1 Activation Plane \(A_g\)

\[
A_g = (DP_g,TP_g,CP_g,R_g,B_g)
\]

where:

- `DP`: sample ownership;
- `TP`: feature/head/hidden compute ownership;
- `CP`: token/context ownership;
- `R`: context carrier/representation;
- `B`: communication backend.

Example context carriers:

- GQA: token KV;
- GDN: prefix/recurrent state;
- HCA: compressed KV;
- CSA: compressed KV + selection/index metadata.

This is the plane where expensive layer-boundary layout transitions may occur.

### 3.2 Parameter Plane \(P_g\)

Defines persistent parameter placement and materialization domain.

- PP substrate: TP sharding plus PP stage ownership.
- FSDP substrate: FSDP sharding and parameter all-gather/materialization domain.

Different layer groups own different parameters, so different static parameter layouts **do not require a runtime parameter remesh at a layer boundary**.

### 3.3 Training-State Plane \(S_g\)

Defines:

- parameter-gradient ownership;
- optimizer-state ownership;
- reduce/reduce-scatter domain;
- outer HSDP/HFSDP synchronization domain.

Parameter, gradient, and optimizer-state ownership need not be identical.

### 3.4 Asymmetric transition rule

Only an incompatible Activation Plane change creates a mandatory layer-boundary redistribution:

\[
T_{g\rightarrow g+1} :
A_g \rightarrow A_{g+1}
\]

Parameter and training-state heterogeneity are normally static per module and do not require layer-to-layer remeshing.

## 4. Hard correctness invariants

No performance experiment is promotable without these invariants.

### C0 — Sample identity

Every logical sample appears exactly once in global training accounting. No repeat replication may be counted as useful throughput.

### C1 — Global batch and token identity

Across compared plans:

- same initial model/optimizer state;
- same logical sample sequence;
- same global valid-token count;
- same loss denominator;
- same gradient-accumulation target.

### C2 — Forward equivalence

Compare final layer output / block output to a reference run with appropriate dtype-specific tolerance.

### C3 — Backward equivalence

Compare:

- input gradients;
- parameter gradients after complete required reductions;
- gradient norms.

### C4 — Optimizer-step equivalence

From identical initial model and optimizer state, run one full optimizer update and compare updated parameters and optimizer state.

### C5 — RNG / recomputation

Dropout, stochastic kernels, checkpoint recomputation, FP8 state, and sequence packing must have explicit alignment rules.

### C6 — Save/resume

Promoted runtime mechanisms must reproduce the same post-resume loss/update trajectory within the project’s calibrated tolerance.

### C7 — Static collective order

All process groups are created before training; collective order is deterministic and deadlock-free.

### C8 — MBS=1 legality

A candidate that increases data-parallel logical sample multiplicity without available independent samples is illegal unless an explicit temporal mechanism such as TMF is selected.

## 5. Paper hypotheses

### H1 — Mixer-local optimum differs

For at least one production-like hybrid pattern:

\[
\arg\min_s T_{\rm GQA}(s)
\neq
\arg\min_s T_{\rm GDN}(s)
\]

or another mixer pair has a similarly meaningful difference.

### H2 — Gross gain survives transition

For `GDN × 3 + GQA`:

\[
3\Delta T_{\rm GDN}+\Delta T_{\rm GQA}
>
2T_{\rm transition}
\]

with margin.

### H3 — Static heterogeneous runtime approaches manual oracle

The generic static runtime should be within ~2% of a manually hard-wired heterogeneous oracle for the same plan.

### H4 — End-to-end gain beats best uniform Megatron

Engineering Go threshold:

- correctness PASS;
- stable >5% end-to-end throughput improvement vs. best measured uniform Megatron plan, **or**
- important new capacity point with competitive speed.

Strong paper signal:

- stable ~8–10%+ improvement on at least one primary full-model workload, with a second workload showing generality or a meaningful negative boundary.

### H5 — Local greedy is insufficient, lightweight global reconciliation is sufficient

Per-mixer local-best assignment should fail on at least one transition-heavy pattern, while a small transition-aware DP/shortest-path selection should approach exhaustive oracle on a tractable subset.

## 6. Phase roadmap

# R0 — Freeze environment and truth source

**Goal:** every agent runs against a reproducible stack.

Record:

- Megatron-LM commit;
- Megatron-Core commit/package version if separate;
- PyTorch version;
- Transformer Engine version;
- CUDA/NCCL versions;
- exact H100 SKU and HBM size;
- node topology / NVLink / NIC topology;
- container hash;
- uncommitted diff.

Create:

- `environment_manifest.json`
- `model_manifest.json`
- `hardware_manifest.json`

**Important current implementation anchors**

As of 2026-09-11 current Megatron docs expose:

- `HyperCommGrid`: arbitrary N-D communication grid;
- `register_view()`: additional factorization of the same rank span;
- Megatron-FSDP `device_mesh`, `dp_shard_dim`, `dp_outer_dim`;
- flattened DP-CP FSDP sharding support;
- current heterogeneous FSDP documentation primarily distinguishes dense/non-expert vs expert meshes.

These are implementation anchors, not assumptions that arbitrary layer-group heterogeneity already works.

**Exit:** one baseline command can be replayed by a different agent and matches step time/memory within expected noise.

# R1 — Opportunity characterization: highest priority

This phase determines whether the paper should exist.

## R1-A — H100 communication calibration

Single-node 8×H100:

Collectives:

- all-gather;
- reduce-scatter;
- all-reduce;
- all-to-all;
- send/recv if used by transition.

Group sizes:

- 2, 4, 8.

Payloads:

- 4 MiB;
- 16 MiB;
- 64 MiB;
- 256 MiB;
- 1 GiB.

Report:

- p50/p95 latency;
- algorithm bandwidth;
- exposed synchronization;
- peak temporary memory.

Two-node extension is conditional.

## R1-B — GQA TP×CP frontier

Fixed:

- 8 H100;
- DP=1;
- PP=1;
- MBS=1;
- same sequence/model shape;
- same dtype/checkpoint setting.

Test legal divisor pairs:

\[
(TP,CP)\in\{(1,8),(2,4),(4,2),(8,1)\}
\]

subject to head/hidden divisibility.

Measure:

- forward;
- backward;
- total block time;
- peak allocated/reserved;
- exposed collective;
- per-rank GPU utilization;
- numerical parity.

## R1-C — GDN TP×CP frontier

Same protocol as GQA using the **current chunkwise production implementation**, not historical headwise data.

Test the same legal pairs.

Record recurrent-state communication separately from TP/CP transition traffic.

## R1-D — Transition microbenchmark

Measure both directions:

- `(1,8) ↔ (2,4)`
- `(1,8) ↔ (4,2)`
- `(2,4) ↔ (4,2)`

Measure:

- forward transition;
- inverse/backward transition;
- round-trip;
- payload bytes;
- peak workspace;
- synchronization/exposed wait.

Implement first with either:

1. Torch DTensor / DeviceMesh prototype;
2. explicit `torch.distributed` collectives;
3. Megatron `HyperCommGrid` views if convenient.

Do not wait for full runtime integration.

## R1-E — Manual macro oracle

Build the smallest faithful macro-block:

\[
\text{GDN} \rightarrow \text{GDN} \rightarrow \text{GDN} \rightarrow \text{GQA}
\]

Compare:

- best uniform legal `(TP,CP)`;
- manually hard-wired mixed plan;
- local-greedy mixed plan if different;
- mixed plan including real transition.

No planner.

### R1 Go / No-Go

**Go to runtime** if:

1. correctness passes;
2. mixed macro beats best uniform by >=5% stably;
3. transition memory does not make the target 128K configuration structurally infeasible.

**Strong Go:** >=8–10%.

**No-Go for heterogeneous Activation Plane** if:

- all mixers prefer the same plan within noise; or
- transition erases gross gain; or
- memory overhead makes the useful plan infeasible.

If No-Go, preserve R1 as a negative result and shift emphasis to Param/State heterogeneity or representation-specific backends.

# R2 — Fast prototype runtime

Only execute after R1 Go.

## R2-A — DTensor prototype

Purpose: prove execution contract quickly.

Required capabilities:

- multiple predeclared mesh views over the same 8 ranks;
- layer-group binding to a view;
- explicit activation redistribution;
- correct backward;
- no runtime mesh creation.

Do not optimize performance beyond removing obvious Python synchronization.

## R2-B — Megatron HyperCommGrid prototype

Use one physical rank span and pre-register required factorization views.

Example conceptual views:

- `gqa`: TP1×CP8;
- `gdn`: TP4×CP2.

Pre-create needed process groups.

Bind layer groups explicitly.

Implement only the transition pairs proven useful in R1.

### Exit

- same outputs/gradients/one-step update as R1 oracle;
- runtime overhead <=2% vs hard-wired oracle;
- no dynamic process-group creation.

---

# R3 — Production static heterogeneous PP substrate

**Goal:** establish the paper’s main runtime result.

Scope:

\[
PP \times DP \times TP_g \times CP_g
\]

with:

- PP fixed at job level;
- DP fixed at job level;
- TP/CP may vary by layer group;
- all views predeclared.

## R3-A — PP=1 full decoder

Run a production-like 14-layer GDN/GQA model.

Sequence lengths:

- 32K;
- 64K;
- 128K.

Compare:

1. best uniform Megatron;
2. manual heterogeneous oracle;
3. generic static heterogeneous runtime.

## R3-B — PP>1

Only after PP=1 succeeds.

Rules:

- stage partition static;
- stage boundary initially uses canonical activation layout;
- heterogeneous views are stage-internal first;
- do not implement cross-stage heterogeneous wire format unless measured stage-boundary normalization cost is material.

## R3-C — Multi-node H100

Preferred topology:

- keep TP×CP high-frequency traffic inside NVSwitch island when possible;
- scale with PP/DP across nodes.

First multi-node test should not add new runtime mechanisms.

### Exit

At least one full-model setting:

- correctness PASS;
- stable >=5% vs best uniform Megatron;
- static runtime within ~2% of manual oracle.

---

# R4 — Correctness certification

Promote from “benchmark prototype” to “training runtime”.

Certification matrix:

- BF16;
- activation recomputation on/off;
- packed sequence if relevant;
- gradient accumulation;
- multiple optimizer steps;
- save/resume;
- deterministic replay where supported.

Required reports:

- `correctness_matrix.csv`
- `post_step_parity.json`
- `resume_parity.json`

A plan/template that fails certification is removed from the usable plan space.

---

# R5 — FSDP Param/State Plane track

This is the second substrate and should not block R1–R4.

Fixed Activation Plane first:

\[
TP=1,\ CP=8,\ DP=1
\]

or another production-relevant fixed activation layout.

Explore static parameter/state factorization:

- FSDP8;
- FSDP4 + state replica factor 2;
- FSDP2 + state replica factor 4;
- HSDP/HFSDP variants if supported by current stack.

Questions:

1. do GQA and GDN have different best FSDP sharding domains?
2. can different layer groups use distinct static parameter/state domains without activation remesh?
3. what is the memory vs exposed AG/RS trade-off?
4. does current Megatron-FSDP permit the required per-module mesh cleanly, or is a small custom wrapper needed?

**Important:** FSDP is not counted as useful compute parallelism.

### Gate F

Promote FSDP heterogeneity only if:

- per-mixer preferred state mesh differs materially;
- end-to-end mixed state plan improves >=5% or unlocks a meaningful capacity point;
- post-step state/gradient equivalence passes.

If not, keep FSDP uniform and do not burden the main paper.

---

# R6 — CSA/HCA secondary workload

Purpose: test generality and demonstrate that the framework does **not** force remeshing.

Start with fixed hidden Activation Plane.

Compare:

- operator-specific representation/backend;
- uniform hidden layout;
- layer-specific hidden remesh only if local data predicts a large gain.

Expected useful result may be:

> CSA/HCA prefer different internal context carriers/backends but the globally optimal plan keeps the same hidden TP/CP layout because transition frequency is too high.

That is a successful boundary result.

MoE/EP remains excluded.

---

# R7 — Optional offline explorer

Only after a manual heterogeneous plan has proven value.

The explorer is **not** part of the runtime critical path.

Input:

- certified template library;
- operator/mixer sequence;
- measured local latency/memory table;
- measured transition table;
- hardware topology;
- memory budget.

Each mixer keeps only 2–5 Pareto/top-k candidates.

Objective:

\[
\min \sum_g T_g(s_g)
+ \sum_g R(s_g,s_{g+1})
\]

subject to memory and legality.

Use dynamic programming / shortest path.

Outputs:

- `parallel_plan.yaml`;
- ranked alternatives;
- explanation of rejected candidates.

Validate against exhaustive enumeration on a small candidate space.

Target:

- planner-selected plan within 1–2% of best measured manual/exhaustive plan on held-out configurations.

---

# R8 — TMF residual branch

TMF is retained only as an optional transition backend.

Use it only if:

1. an operator wants lower CP;
2. TP/head/state intra-sample parallelism cannot consume the released ranks;
3. increasing DP is otherwise necessary;
4. MBS=1 lacks spatial independent samples;
5. gross operator gain exceeds temporal wait + transition + activation-memory cost.

Do not optimize streaming/cohort granularity before such a workload is proven.

## 7. H100 topology strategy

### Single-node 8×H100

Highest-frequency candidate dimensions should remain node-local:

- TP;
- CP;
- TP↔CP transition;
- FSDP inner AG/RS when FSDP track is used.

This is the primary rapid-validation environment.

### Two or more nodes

Prefer:

- TP×CP within node;
- DP and/or PP across nodes;
- HSDP/HFSDP outer synchronization across nodes when used.

Only test cross-node CP when sequence length/capacity requires CP > 8 or when the paper explicitly studies hierarchical CP.

Do not mix cross-node CP into the first opportunity experiment.

## 8. Measurement protocol

Every official performance point:

- >=3 warmup complete iterations after initialization/JIT;
- >=5 measured iterations;
- repeat independent launches for competitive final points;
- formal final comparison: >=3 launches, expand to 5 if close/noisy;
- no profiler in throughput runs.

Report:

- median step time;
- unique valid tokens/s;
- all-rank max peak allocated;
- all-rank max peak reserved;
- exposed collective wait;
- transition time;
- communication bytes;
- forward/backward split;
- correctness status.

Status vocabulary:

- PASS
- CORRECTNESS_FAIL
- OOM
- RUNTIME_FAIL
- NOT_RUN

Never encode failure as zero time.

## 10. Earliest paper decision checkpoints

### Decision D1 — after local frontier + transition

Question:

> Do GQA and GDN have sufficiently different local optima, and is transition cheap enough to plausibly survive?

If no: stop ActivationMesh runtime work.

### Decision D2 — after manual `3GDN+1GQA` oracle

Question:

> Does a real mixed plan beat best uniform >=5%?

If no: do not build a general runtime.

### Decision D3 — after generic static runtime

Question:

> Is runtime overhead <=2% vs manual oracle?

If no: optimize mechanism before planner/FSDP/CSA-HCA.

### Decision D4 — after full decoder 64K/128K

Question:

> Does the gain survive full FFN/loss/optimizer/memory behavior?

If no: paper may remain an operator-level negative result; do not scale out.

## 11. Paper structure if D1–D4 pass

1. **Motivation:** hybrid sequence mixers invalidate one-global-layout assumption.
2. **Characterization:** GQA/GDN/CSA/HCA have different communication regimes on H100.
3. **Execution contract:** Activation / Parameter / State ownership planes.
4. **Static heterogeneous runtime:** predeclared views, layer-group binding, activation transitions.
5. **Correctness:** sample, gradient, optimizer, RNG, checkpoint contracts.
6. **Optional explorer:** small measured candidate set + transition-aware DP.
7. **Evaluation:** best tuned Megatron uniform vs manual oracle vs runtime vs explorer.
8. **Boundaries:** CSA/HCA may prefer fixed hidden layout; TMF only residual.

Primary performance claim should be phrased like:

> Using identical Megatron kernels, precision, batch semantics, and hardware, replacing a globally uniform parallel configuration with a predeclared static heterogeneous execution plan improves end-to-end hybrid-model training throughput by X%.

## 12. Explicit non-goals for the first paper

- no MoE/EP integration;
- no online/dynamic planner;
- no per-step process-group creation;
- no arbitrary graph compiler;
- no requirement to outperform Megatron through custom kernels;
- no SFT/RL dynamic-length planner;
- no mandatory TMF;
- no simultaneous PP+FSDP optimization;
- no claim of global optimum over arbitrary parallel strategies.

---

## 13. Stop conditions

Stop or pivot the main heterogeneous Activation Plane direction if any is true:

1. GQA/GDN local best layouts are effectively identical.
2. Best mixed macro gain is <5% after transition.
3. 128K mixed plan is structurally memory-infeasible and no equivalent lower-memory transition exists.
4. Correctness requires changing user-visible training semantics.
5. Generic runtime adds >5% overhead relative to hard-wired oracle after focused optimization.
6. Benefit only exists against a weak/default Megatron baseline but disappears against best tuned uniform Megatron.

If stopped, the remaining viable paper directions are:

- FSDP Param/State heterogeneity;
- context-representation/backend specialization;
- a negative study showing why dynamic hidden remeshing is not worthwhile on modern hybrid backends.

## 14. Immediate execution order

Run these **in parallel** as soon as GPUs are available:

1. H100 collective calibration.
2. GQA TP×CP frontier.
3. GDN TP×CP frontier.
4. DTensor / explicit-collective transition prototype.
5. Environment/API audit of latest Megatron `HyperCommGrid`, GDN/GQA paths, and current FSDP hooks.

As soon as 2–4 finish:

6. build the manual `3GDN+1GQA` mixed oracle;
7. make D1/D2 Go/No-Go.

Only after D2 Go:

8. build Megatron static heterogeneous runtime;
9. run full 14-layer 32K/64K/128K;
10. then start FSDP state-plane, CSA/HCA, and offline explorer lanes.

This ordering is intentionally designed to obtain the highest-value research decision before substantial framework engineering.
